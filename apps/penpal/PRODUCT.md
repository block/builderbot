# Penpal: Product Requirements

Penpal is a desktop app and local web server for **collaborative document review between humans and AI agents**. It operates on markdown files inside `thoughts/` directories — research, plans, guides, and other prose artifacts that agents produce during software development. It is NOT a code review tool.

The system has three components: a **desktop app** (macOS, wraps the web UI with native tabs and windows), a **Go server** (serves the web UI, manages comments, exposes an MCP endpoint), and a **Claude Code plugin** (skills + MCP tool definitions that let agents participate in review).

---

## Supported Source Types

Penpal discovers and displays markdown files from several source types. Requirements that say "all source types" apply to every type listed here.

| Source Type | Location | Description |
|---|---|---|
| **rp1 thoughts** | `thoughts/` subdirectory in any directory | The primary source. Each directory containing `thoughts/` is a "project." |
| **Claude plans** | `~/.claude/plans/` | Plan files generated by Claude Code. |
| **rp1 trees** | `.rp1/` directory in any project | Organized by type: features, issues, context, quick builds. |
| **Manual sources** | User-specified path | Any directory of markdown files explicitly added by the user. |

### rp1 thoughts

- **SRC-THOUGHTS-SCAN**: Scan the filesystem for directories containing a `thoughts/` subdirectory. Each such directory becomes a project.
- **SRC-THOUGHTS-TITLE**: Use the parent directory name as the project name (e.g., `~/dev/myapp/thoughts/` → project "myapp").
- **SRC-THOUGHTS-FLAT**: Display all markdown files within `thoughts/` as a flat list within the project, preserving any subdirectory structure for grouping.

### Claude plans

- **SRC-PLANS-PATH**: Discover plan files from `~/.claude/plans/`. Surface them as a single virtual project.
- **SRC-PLANS-READONLY**: Plan files are read-only in penpal — they are generated and managed by Claude Code.
- **SRC-PLANS-NAMING**: Display plans using their document title (first `#` heading) rather than the filename.

### rp1 trees

- **SRC-RP1-DETECT**: Auto-detect `.rp1/` directories within projects.
- **SRC-RP1-GROUPING**: Organize rp1 files by type (features, issues, context, quick builds) with grouped display and badges.
- **SRC-RP1-BADGES**: Display type badges based on the rp1 file category.

### Manual sources

- **SRC-MANUAL-ADD**: Users can manually add any directory as a source via the UI.
- **SRC-MANUAL-PERSIST**: Manually added sources are persisted across restarts.
- **SRC-MANUAL-REMOVE**: Users can remove manually added sources.

## 1. Project Discovery

### Auto-Discovery

- **DISC-AUTO**: On startup, scan the filesystem for all supported source types (see table above). Display all discovered projects in the sidebar.

- **DISC-RUNTIME**: Detect new source directories at runtime without requiring a restart. Applies to all source types.

- **DISC-DEDUP**: De-duplicate files that appear in overlapping source directories so each file appears once.

### Git Integration

- **DISC-GIT-BRANCH**: Display the current git branch for each project.

- **DISC-GIT-STATUS**: Show git status (clean, dirty, ahead/behind) per project.

## 2. Document Viewing

### Markdown Rendering

- **VIEW-RENDER**: Render markdown with full CommonMark support, syntax-highlighted code blocks, and inline mermaid diagram rendering (fenced `mermaid` blocks rendered as SVGs).

- **VIEW-LIVE**: Watch files on disk and live-reload content in the browser via SSE when a file changes. No manual refresh required.

- **VIEW-TOC**: Display a sidebar table of contents generated from document headings. Headings with bold, italic, code, or links render correctly.

- **VIEW-TITLE**: Parse files for their document title (first `#` heading) and display it instead of the raw filename.

- **VIEW-SOURCE-LINE**: Track source line numbers through the rendering pipeline so that UI features (comments, selection) can map back to file positions.

### Navigation

- **VIEW-SEARCH**: Full-text search across all files in all projects.

- **VIEW-FIND**: In-page find (Cmd+F) within the currently displayed document.

- **VIEW-HISTORY**: Each tab maintains its own back/forward navigation history with toolbar buttons and keyboard shortcuts (Cmd+[ / Cmd+]).

### Selection & Interaction

- **VIEW-COPY-MD**: Select text in a rendered document and copy the raw markdown source for that selection to the clipboard.

- **VIEW-EXPAND-IMG**: Hover over any image or mermaid diagram to reveal an "Expand" button that opens a near-fullscreen modal.

## 3. Comment Threads

Comment threads are the core collaboration primitive. They are anchored to specific text in a document, like Google Docs comments.

### Creating Threads

- **THREAD-CREATE-TEXT**: Select text in a rendered document to anchor a new comment thread to that selection.

- **THREAD-CREATE-MERMAID**: Select an area on a rendered mermaid diagram to anchor a comment thread to that diagram region.

- **THREAD-ANCHOR**: Comments store the selected text and heading path for anchoring. Highlights are stable across edits as long as the anchor text is still present.

### Thread Lifecycle

- **THREAD-REPLY**: Any participant (human or agent) can reply to a thread.

- **THREAD-RESOLVE**: Only humans can resolve threads. Agents must never resolve threads — they reply and let the human decide when the conversation is done.

- **THREAD-REOPEN**: Resolved threads can be reopened.

- **THREAD-SUGGESTED-REPLIES**: Agents can attach up to 3 short suggested replies (clickable pills) to their comments, so humans can respond with one tap instead of typing.

### Highlighting

- **THREAD-HIGHLIGHT-RENDER**: Render a visible highlight (background color) over the anchored text for every open thread. Highlights are rendered inline in the document content, not as DOM overlays.

- **THREAD-HIGHLIGHT-PERSIST**: Highlights persist across file reloads and live-reload updates. When a file changes on disk, re-anchor highlights to the updated content.

- **THREAD-HIGHLIGHT-ACCURACY**: Highlights must cover exactly the anchored text — no partial words, no bleeding into adjacent content. Use the stored selected text and heading path to locate the correct range.

- **THREAD-HIGHLIGHT-OVERLAP**: When multiple threads anchor to overlapping text, render all highlights without visual corruption. Overlapping regions should use a darker or combined highlight color.

- **THREAD-HIGHLIGHT-RESOLVED**: Hide highlights for resolved threads. Restoring a highlight when a thread is reopened.

### Scroll & Focus

- **THREAD-SCROLL-TO-HIGHLIGHT**: Clicking a thread in the comments panel scrolls the document to bring the corresponding highlight into view.

- **THREAD-SCROLL-TO-THREAD**: Clicking a highlight in the document scrolls the comments panel to the corresponding thread and visually focuses it.

- **THREAD-SCROLL-SMOOTH**: Scroll animations are smooth, not instant jumps.

### Storage

- **THREAD-LOCAL**: Comment data is stored locally on disk in a `.penpal/` directory alongside the project. Comments are not synced to any remote service.

## 4. Review Workflow

Review is implicit — a file is "in review" whenever it has open comment threads. There is no explicit "request review" step.

### In Review

- **REVIEW-IN-REVIEW**: A global "In Review" page shows all files across all projects that have open comment threads.

- **REVIEW-PROJECT-SURFACE**: Within each project page, files with active threads are surfaced at the top of the file list.

### Agent Monitoring

- **REVIEW-AGENT-MONITOR**: An agent can enter a monitoring loop: it watches for new or updated threads, reads the document for context, and replies. The agent stays active until all threads are resolved or the human dismisses it.

- **REVIEW-AGENT-WAIT**: The MCP `wait_for_changes` tool blocks for up to 30 seconds and returns immediately when comment activity occurs. This is the agent's event loop primitive.

- **REVIEW-AGENT-PRESENCE**: When an agent is actively monitoring a file, display a presence indicator in the UI so the human knows the agent is watching.

- **REVIEW-AGENT-CONTEXT**: Show the agent's context window usage in real time so the human can gauge how much runway the agent has left.

- **REVIEW-AGENT-WORKING**: While an agent is processing a thread, show a working indicator on that thread. The agent's reply is what signals completion.

## 5. Desktop App

### Native Shell

- **APP-MACOS**: macOS desktop application (Tauri-based). Wraps the web UI with native chrome.

- **APP-TABS**: Multiple tabs within a single window with standard keyboard shortcuts (Cmd+T, Cmd+W, Cmd+Shift+]).

- **APP-WINDOWS**: Multiple window support.

- **APP-MENU-BAR**: Menu bar icon for quick access. Dev builds show "Penpal Dev" to distinguish from Homebrew installs.

### First-Run Setup

- **APP-INSTALL-PROMPT**: On first launch, prompt the user to install the CLI (`penpal` command) and the Claude Code plugin.

- **APP-INSTALL-CLI**: Install the `penpal` binary to the user's PATH.

- **APP-INSTALL-PLUGIN**: Install the Claude Code MCP plugin that registers penpal tools and skills.

## 6. CLI

- **CLI-OPEN**: `penpal open <path>...` opens one or more files in the desktop app. Launches the app if needed, adds the file to the project, and navigates to it.

## 7. MCP Server

The Go server exposes an MCP endpoint at `/mcp` so AI agents can participate in document review programmatically via the Model Context Protocol.

### Tools

- **MCP-FIND-PROJECT**: `penpal_find_project` — given a working directory, return the project name. Agents call this first if they don't know their project.

- **MCP-FILES-IN-REVIEW**: `penpal_files_in_review` — list all files with open threads, including thread details and the oldest pending thread (where the last comment is from a human).

- **MCP-WAIT**: `penpal_wait_for_changes` — long-poll for comment activity. Blocks up to 30s, returns immediately on change. Also maintains the agent heartbeat for presence indication.

- **MCP-LIST-THREADS**: `penpal_list_threads` — list threads on a file, optionally filtered by status.

- **MCP-READ-THREAD**: `penpal_read_thread` — read a full thread with all replies.

- **MCP-CREATE-THREAD**: `penpal_create_thread` — create a new thread anchored to selected text.

- **MCP-REPLY**: `penpal_reply` — reply to an existing thread, with optional suggested replies.

## 8. Activity & Recency

- **ACTIVITY-RECENT**: A "Recent" page shows the latest activity across all projects — file edits, new comments, replies — with labels like "edited" and "commented."

- **ACTIVITY-STARTUP**: The Recent page populates immediately on startup from recently modified files, rather than starting empty and only tracking runtime changes.

---

## 9. Publishing

- **PUBLISH-BLOCKCELL**: Publish any document as a standalone HTML site with a TOC sidebar, mermaid diagram support, and a copy-markdown button.

---

## 10. Appearance

- **THEME-TOGGLE**: Light and dark mode with a toggle. Defaults to system preference.

- **THEME-MERMAID**: Mermaid diagrams respect the current theme (light or dark).

- **VIEW-RESIZE-COMMENTS**: The comments panel is resizable by dragging.

---

## 11. File Management

- **MANAGE-BULK**: Select multiple files or entire sources to delete or manage in bulk, with a selection bar showing singular/plural counts.

- **MANAGE-BADGES**: Files display type badges (research, plan, etc.) based on their path or content.

- **MANAGE-GROUPING**: Files are grouped by source directory and displayed with their project structure.

---

## 12. Trust & Human Oversight

- **TRUST-HUMAN-RESOLVES**: Only humans resolve comment threads. The agent's role is to reply and make changes — the human decides when a conversation is done.

- **TRUST-AGENT-SCOPED**: Agents operate only on markdown files in `thoughts/` directories. They cannot modify source code through penpal.

- **TRUST-LOCAL**: All data stays local. Comments are stored on disk. No data is sent to external services (except when explicitly publishing via Blockcell).

---

## 13. Open Questions

- **OPEN-HOSTED**: Should penpal support hosted mirrors with synced comment threads for human-to-human collaboration across machines?

- **OPEN-PLUGGABLE-AGENTS**: How should agents be made pluggable? Currently tightly coupled to Claude Code via MCP plugin.

- **OPEN-SHARED-STACK**: Should penpal share a tech stack with the other apps in the builderbot monorepo (Mark, Staged)?

- **OPEN-COMMENT-LIBRARY**: Should the comment thread system be extracted as a reusable library for other tools?

- **OPEN-EXTERNAL-LINKS**: How should links to external sites behave? Currently open in the default browser rather than inside the app.
